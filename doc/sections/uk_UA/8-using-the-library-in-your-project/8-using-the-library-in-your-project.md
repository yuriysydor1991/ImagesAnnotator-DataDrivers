# Використання бібліотеки у власному проекті

Дана секція є посібником з інтеграції на боці проекту-споживача: що встановлювати, що писати у власному `CMakeLists.txt`, як підключати заголовкові файли і як виглядає повноцінна робоча програма. Показані нижче CMake-проект і програма були скомпільовані, злінковані і запущені зі встановленою бібліотекою.

Вихідні коди бібліотеки для її використання не потрібні. Сконфігуруй, побудуй і встанови їх один раз - або встанови зібраний з них пакунок - і твій власний проект бачитиме виключно встановлений CMake-пакет.

## 1. Встановлення бібліотеки

Побудова і встановлення є звичайними і детально описані у секціях [побудова проекту](/doc/sections/uk_UA/5-project-build/5-project-build.md) і [встановлення](/doc/sections/uk_UA/7-installing/7-installing.md):

```
git clone https://github.com/yuriysydor1991/ImagesAnnotator-DataDrivers.git
cd ImagesAnnotator-DataDrivers

cmake -S . -B build
cmake --build build -j$(nproc)

sudo cmake --install build --prefix "/usr"
```

Після чого у системі залишається наступне:

| Що встановлено | Шлях (для показаного вище префікса `/usr`) |
| --- | --- |
| динамічна бібліотека | `/usr/lib/libImagesAnnotatorDataDrivers-0.13.so.0.13.0` разом із посиланням soname `.so.0` і посиланням для розробки `.so` |
| публічні заголовкові файли | `/usr/include/ImagesAnnotatorDataDrivers-0.13/` - усі одинадцять |
| CMake-пакет | `/usr/lib/cmake/ImagesAnnotatorDataDrivers-0.13/` |

Прибери `--prefix` і усе потрапить під `/usr/local` натомість, що є значенням за замовчуванням і є цілком прийнятним доти, доки твій набір інструментів заглядає туди.

Дві речі, про які не варто турбуватись: бібліотека не потребує від тебе жодної реалізації логера - компонент журналювання вкомпільовано безпосередньо у неї - і жодна з трьох її залежностей не витікає назовні. nlohmann/json, libcurl і zlib лінкуються **приватно**, жоден публічний заголовковий файл не згадує їхніх типів, отож твій проект не додає жодної з них до свого шляху пошуку підключаємих файлів і не викликає `find_package` для жодної з них. Однак libcurl і системна zlib залишаються звичайними залежностями встановленого бінарного файлу від динамічних бібліотек, отож вони мають залишатись присутніми у системі так само, як і libstdc++.

## 2. Файл `CMakeLists.txt` проекту-споживача

```cmake
cmake_minimum_required(VERSION 3.13)
project(MyTool LANGUAGES CXX)

set(CMAKE_CXX_STANDARD 17)
set(CMAKE_CXX_STANDARD_REQUIRED ON)

find_package(ImagesAnnotatorDataDrivers-0.13 REQUIRED)

add_executable(mytool main.cpp)
target_link_libraries(mytool ImagesAnnotatorDataDrivers-0.13::ImagesAnnotatorDataDrivers-0.13)
```

Тут відбуваються чотири речі, і усі чотири мають значення:

- **Стандарт C++17 є обов'язковим.** Публічні заголовкові файли використовують `std::filesystem` і вбудовані статичні поля даних. Старіший стандарт їх не скомпілює.
- **Пакет названий за іменем бібліотеки, включно з головним номером версії** - `ImagesAnnotatorDataDrivers-0.13`. Версія є частиною імені навмисне: майбутній `ImagesAnnotatorDataDrivers-1` встановиться поруч, а не поверх нього.
- **Імпортована ціль розміщена у просторі імен з тією ж самою назвою**, звідси і дещо надлишковий на вигляд запис `ImagesAnnotatorDataDrivers-0.13::ImagesAnnotatorDataDrivers-0.13`. Лінкування цілі є усім, що потрібно зробити: вона несе директорії підключаємих файлів разом із собою, отож жодного власного `target_include_directories` не потрібно.
- **Запитуй пакет без вимоги версії.** Директорія встановленого пакета містить лише файли конфігурації і експортованих цілей, отож `find_package(ImagesAnnotatorDataDrivers-0.13 0.13 REQUIRED)` з версією всередині не розв'яжеться. Саме головний номер версії, вкарбований у назву пакета, розводить несумісні випуски, а `IADataDriversFacade::library_version()` повідомляє точну версію під час виконання.

Якщо бібліотека потрапила у префікс, який твій CMake сам не переглядає, вкажи йому на нього під час конфігурації власного проекту:

```
cmake -S . -B build -DCMAKE_PREFIX_PATH="$HOME/.local"
```

І зауваження для екзотичних випадків: встановлювана назва не є висіченою у камені. Параметри побудови бібліотеки `LIB_INCLUDE_MINOR_IN_NAME`, `LIB_INCLUDE_MICRO_IN_NAME` і `LIB_NAME_SUFFIX` змінюють одночасно назву бінарного файлу, піддиректорію заголовкових файлів, директорію CMake-пакета і простір імен імпортованої цілі - див. [налаштування складових імені встановлюваної бібліотеки](/doc/sections/uk_UA/5-project-build/compression/5-23-customizing-library-name-segments.md). Побудуй бібліотеку з ними - і назва у `find_package` твого проекту має слідувати за ними, наприклад `ImagesAnnotatorDataDrivers-0.13`.

## 3. Підключення заголовкових файлів

Для встановленої бібліотеки працюють обидва наступні варіанти, оскільки пакет експортує корінь директорії підключаємих файлів разом з її версіонованою піддиректорією:

```cpp
#include <ImagesAnnotatorDataDrivers-0.13/IADataDriversFacade.h>   // рекомендовано
#include <IADataDriversFacade.h>                                   // теж працює
```

Надавай перевагу формі з префіксом. Назви заголовкових файлів на кшталт `ImageRecord.h`, `IRecord.h` чи `IADataDriversLib.h` є достатньо загальними, щоб призвести до конфлікту з чимось іншим у завантаженому шляху пошуку підключаємих файлів, а префікс з першого погляду показує, звідки походить заголовковий файл.

`IADataDriversFacade.h` притягує усе, що потрібно звичайному споживачеві - контекст, інтерфейси бази даних і типи записів приходять разом з ним. Підключай окремі заголовкові файли безпосередньо тоді, коли реалізуєш одну з точок розширення, наприклад `<ImagesAnnotatorDataDrivers-0.13/IDBMerger.h>`.

І ще простір імен. Кожен публічний тип знаходиться у `ImagesAnnotatorDataDrivers013`, де `013` є склеєними головним і другорядним номерами версії бібліотеки, щоб дві версії бібліотеки могли співіснувати в межах однієї одиниці трансляції. Створи для нього псевдонім один раз:

```cpp
namespace iadd = ImagesAnnotatorDataDrivers013;
```

Підняття версії коштуватиме тоді рівно один рядок.

## 4. Повноцінний приклад програми

`main.cpp` - виводить кожен запис зображення з файлу проекту разом з кількістю його прямокутників і перезаписує файл лише тоді, коли справді щось змінилось:

```cpp
#include <iostream>
#include <ImagesAnnotatorDataDrivers-0.13/IADataDriversFacade.h>

namespace iadd = ImagesAnnotatorDataDrivers013;

int main(int argc, char** argv)
{
  if (argc < 2) { return 1; }

  auto db = iadd::IADataDriversFacade::open_annotations_db(argv[1]);

  if (db == nullptr) { return 1; }

  for (const auto& ir : db->get_images_db()) {
    std::cout << ir->get_full_path() << " rects=" << ir->rects.size() << "\n";
  }

  return db->changed() ? (db->store_db() ? 0 : 1) : 0;
}
```

Побудова і запуск:

```
cmake -S . -B build
cmake --build build -j$(nproc)

./build/mytool /path/to/annotations-project.json
```

Попри свій розмір, програма вже демонструє увесь життєвий цикл:

- `open_annotations_db()` створює базу даних і завантажує файл одним викликом, повертаючи `nullptr`, коли файл відсутній, нечитабельний або не є коректним проектом анотацій;
- `get_images_db()` віддає **змінюване посилання** на записи, отож цикл є також і місцем, де ти редагував би `ir->rects` - записи є розумними вказівниками і жодного окремого кроку "фіксації" немає;
- `changed()` порівнює живі записи зі знімком, зробленим під час завантаження, отож `store_db()` відбувається лише тоді, коли запис справді дав би щось інше.

Усе інше - побудова через контекст, шлях одного пострілу `IADataDriversLib::libcall()`, поля записів, точки розширення `IRecordsFactory` і `IDBMerger` - описано у секції [API бази даних анотацій](/doc/sections/uk_UA/4-project-structure/4-9-the-annotations-database-api.md), а файл, який зчитує програма, специфіковано у секції [формат JSON-файлу проекту анотацій](/doc/sections/uk_UA/4-project-structure/4-10-the-annotations-project-json-format.md).

## 5. Запис нового файлу проекту

Інша половина роботи - побудова бази даних з нуля замість зчитування наявної - є так само короткою. Створи записи через фабрику, передай їх, вкажи місце призначення:

```cpp
#include <ImagesAnnotatorDataDrivers-0.13/IADataDriversFacade.h>

namespace iadd = ImagesAnnotatorDataDrivers013;

bool write_project(const std::string& outPath)
{
  auto factory = iadd::IADataDriversFacade::create_records_factory();
  auto db = iadd::IADataDriversFacade::create_annotations_db();

  if (factory == nullptr || db == nullptr) { return false; }

  auto ir = factory->create_image_record("cats/001.png", "/data/images");

  ir->iwidth = 1920;
  ir->iheight = 1080;
  ir->rects.emplace_back(
      factory->create_image_rect_record("cat", 10, 20, 100, 200));

  db->add_images_db({ir});

  return db->store_db(outPath);
}
```

Зверни увагу на місце призначення: база даних, яку ніколи не завантажували з файлу і ніколи не зберігали у файл, не має типового шляху, отож першим збереженням має бути перевантаження `store_db(fpath)`. Далі вже безаргументний `store_db()` записує у те саме місце.

## 6. Як сам ImagesAnnotator використовує бібліотеку

Код цієї бібліотеки раніше був компонентом `src/annotator-business/dbs/AnnotationsDBs` застосунку [ImagesAnnotator](https://github.com/yuriysydor1991/ImagesAnnotator.git). Застосунок має позбутися тієї копії всередині свого дерева і використовувати натомість встановлену бібліотеку, саме через показані вище `find_package` і ціль у просторі імен.

Міграція є радше справою назв, аніж логіки, оскільки винесені інтерфейси зберегли свої: `IAnnotationsDB`, `IImagesPathsDBProvider`, `ImageRecord`, `ImageRecordRect`, `IRecordsFactory` і `IDBMerger` є тими самими абстракціями, під які застосунок вже був написаний. Змінюється те, звідки вони походять - встановлені заголовкові файли `ImagesAnnotatorDataDrivers-0.13/` замість локального відносного підключення - і те, що вони тепер знаходяться у версіонованому просторі імен `ImagesAnnotatorDataDrivers013`, який поглинається псевдонімом. Конкретна побудова `AnnotationsDirDB` замінюється викликом `IADataDriversFacade`, а ідентичність кореневого елемента JSON зберігає своє типове значення `"ImagesAnnotator"` саме для того, щоб кожен файл проекту, записаний кожним попереднім випуском застосунку, продовжував відкриватись - див. [налаштування ідентичності бази даних анотацій](/doc/sections/uk_UA/5-project-build/5-36-configuring-the-annotations-db-identity.md).

Експортери наборів даних того застосунку - у простий текст, YOLO v4 і PyTorch-Vision - **не** є частиною даної бібліотеки і не плануються нею: вони мають стати окремим власним проектом.

## 7. Якщо воно не лінкується

Кілька звичних підозрюваних:

- `find_package` не знаходить пакет - префікс не переглядається. Передай `-DCMAKE_PREFIX_PATH=<префікс>` і перевір, що `<префікс>/lib/cmake/ImagesAnnotatorDataDrivers-0.13/ImagesAnnotatorDataDrivers-0.13Config.cmake` справді там є.
- Назву цілі відхилено - пам'ятай, що вона подвоєна: `ImagesAnnotatorDataDrivers-0.13::ImagesAnnotatorDataDrivers-0.13`. А якщо бібліотеку було побудовано з параметрами складових імені, то й уся назва відрізняється.
- Заголовкові файли не знаходяться, хоча пакет знайдено - найімовірніше, ти лінкуєш просту назву бібліотеки замість імпортованої цілі у просторі імен і, відповідно, не отримуєш жодної з її вимог використання.
- Програма будується, але не запускається, скаржачись на `libImagesAnnotatorDataDrivers-0.13.so.0` - директорія `lib` префікса встановлення не входить до шляху пошуку динамічного завантажувача. Виконай `sudo ldconfig` після встановлення або встанови `LD_LIBRARY_PATH` для нестандартного префікса.
