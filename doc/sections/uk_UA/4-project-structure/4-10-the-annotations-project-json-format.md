## Формат JSON проекту анотацій

Проект анотацій - це єдиний JSON-документ. Ця секція описує його таким, яким його насправді реалізує бібліотека - назви полів походять з [AnnotationsJSONSerializator.h](/src/lib/libmain/dbs/AnnotationsDBs/AnnotationsJSONSerializator.h), правила читання - з конвертерів у [src/lib/libmain/dbs/AnnotationsDBs/converters](/src/lib/libmain/dbs/AnnotationsDBs/converters), а правила перевірки - з [AnnotationsJSONSerializator.cpp](/src/lib/libmain/dbs/AnnotationsDBs/AnnotationsJSONSerializator.cpp).

Ніщо тут не є приватною деталлю: формат - це і є весь сенс бібліотеки, і файл, який вона пише, має залишатися читабельним для застосунку [ImagesAnnotator](https://github.com/yuriysydor1991/ImagesAnnotator.git) і для будь-чийого стороннього інструментарію.

### Загальний вигляд одним поглядом

```
кореневий об'єкт
  "<app name>": { "version": "<app version>" }   елемент ідентичності
  "annotations": [                               вихідні теки
    { "db": { "path": "<absolute dir path or URL>" },
      "annotations": [                           записи зображень тієї теки
        { "rel_path": "<path relative to db.path>",
          "scale_factor": <double>,
          "width":  <int>,
          "height": <int>,
          "annotations": [                       прямокутники того зображення
            { "name": "<class name>",
              "rect": { "x": <int>, "y": <int>,
                        "width": <int>, "height": <int> } } ] } ] } ]
```

Три рівні, і ключ `"annotations"` повторно вживається на кожному з них - один раз як масив вихідних тек, один раз як масив зображень усередині теки, один раз як масив прямокутників усередині зображення. Розрізняє їх саме вкладеність.

Є і друге повторне вживання, про яке варто знати: `"width"` і `"height"` означають власний розмір **зображення**, коли вони стоять поруч із `"rel_path"`, і розмір **прямокутника**, коли вони стоять усередині `"rect"`. Обидва написання - це буквально ті самі константи у коді.

### Кореневий об'єкт

| Поле | Тип | Обов'язкове | Значення |
| --- | --- | --- | --- |
| `<app name>` | об'єкт | **так** | елемент ідентичності, названий іменем *застосунку*. `"ImagesAnnotator"` за замовчуванням |
| `<app name>.version` | рядок | **так** | версія застосунку, що записав файл |
| `annotations` | масив | **так** | групи вихідних тек |

Ім'я кореневого елемента - це не ім'я бібліотеки і не сталий літерал; це те, чим налаштовано примірник бази даних. Це рішення заради сумісності, і секція [налаштування ідентичності бази даних анотацій](/doc/sections/uk_UA/5-project-build/5-36-configuring-the-annotations-db-identity.md) пояснює його вповні. Коротка версія: файли, записані ImagesAnnotator, несуть корінь `"ImagesAnnotator"`, тож бібліотека за замовчуванням бере це ім'я і дозволяє перевизначити його під час побудови або під час виконання.

Читач шукає кореневий елемент **за тим іменем, яким його налаштовано**. Прочитайте файл із коренем `"ImagesAnnotator"` базою даних, налаштованою на `"MyTool"`, і вийде невдача - не тому, що документ спотворений, а тому, що він належить комусь іншому.

### Група вихідної теки

| Поле | Тип | Обов'язкове | Значення |
| --- | --- | --- | --- |
| `db` | об'єкт | **так** | опис джерела |
| `db.path` | рядок | **так**, непорожній | абсолютний шлях до директорії, або URL веб-сторінки, звідки взято зображення |
| `annotations` | масив | **так** | записи зображень, що належать цьому джерелу |

Групування не є косметичним: `db.path` стає `abs_dir_path` кожного запису всередині групи, і це та половина розташування зображення, яка не повторюється для кожного запису. Під час запису записи перегруповуються за їхніми `abs_dir_path`, а групи виходять упорядкованими за цим шляхом.

### Запис зображення

| Поле | Тип | Обов'язкове | Відображається у | Значення |
| --- | --- | --- | --- | --- |
| `rel_path` | рядок | **так** | `ImageRecord::path` | шлях до зображення відносно охоплюючого `db.path` |
| `scale_factor` | double | необов'язкове | `ImageRecord::imageScale` | масштаб попереднього перегляду. Відсутність означає `0` - "користувач ще не обрав масштаб" |
| `width` | int | необов'язкове | `ImageRecord::iwidth` | власна ширина зображення. Відсутність означає `0` |
| `height` | int | необов'язкове | `ImageRecord::iheight` | власна висота зображення. Відсутність означає `0` |
| `annotations` | масив | **так** | `ImageRecord::rects` | прямокутники, намальовані поверх цього зображення |

Три необов'язкові поля справді є необов'язковими під час читання - кожне береться лише тоді, коли ключ присутній, тож написаний вручну файл може не містити жодного з них. Записувач, натомість, завжди їх видає, тож файл, що пройшов цикл збереження, несе їх усі, навіть коли вони нульові.

`ImageRecord::tmppath` і `ImageRecord::current_rect` ніколи не з'являються у документі. Перше - це шлях локального мережевого кешу, а друге - виділення, і жодне з них нічого не означає для іншої машини чи іншого сеансу.

### Прямокутник

| Поле | Тип | Обов'язкове | Відображається у |
| --- | --- | --- | --- |
| `name` | рядок | **так** | `ImageRecordRect::name` - ім'я анотації (класу) |
| `rect` | об'єкт | **так** | геометрія |
| `rect.x` | int | **так** | `ImageRecordRect::x` |
| `rect.y` | int | **так** | `ImageRecordRect::y` |
| `rect.width` | int | **так** | `ImageRecordRect::width` |
| `rect.height` | int | **так** | `ImageRecordRect::height` |

Координати подані у власному піксельному просторі зображення, ніколи не у масштабованому просторі попереднього перегляду, тож `scale_factor` жодним чином не впливає на те, як слід тлумачити прямокутник.

- **Ключі `"scale_factor"` усередині об'єктів прямокутників ігноруються.** Прямокутник читається лише заради його `name` і його `rect`; масштаб зображення є полем рівня запису зображення. Фікстура несе їх саме тому, що реальний файл може містити сміття у місці, для якого формат нічого не визначає.
- **Ніщо не вимагає, щоб записи були відсортовані у документі.** Сортування за повним шляхом відбувається під час злиття, а не під час завантаження: завантаження передає записи рівно у тому порядку, у якому їх перелічує файл.

### Розбіжність версій: попередження, а не відмова

Коли версія в елементі ідентичності відрізняється від версії, якою налаштовано базу даних, бібліотека записує попередження у журнал і **продовжує завантаження**:

```
file's ImagesAnnotator app version is: 0.10.0
Current app version and files's ones missmatch: 0.10.0 != 0.11.0
```

Це навмисно. Формат був стабільним, версія є інформаційним штампом, а відмова від файлу, записаного трохи старішим або трохи новішим застосунком, була б значно гіршим режимом відмови, ніж рядок у журналі. Не варто будувати власну логіку поверх рядка версії, очікуючи, що бібліотека щось стосовно нього забезпечуватиме.

### Що робить документ недійсним

`load_db()` повертає `false` - а `LibraryFacade::open_annotations_db()` повертає `nullptr` - у будь-якому з цих випадків:

| Причина | Подробиці |
| --- | --- |
| шлях порожній, або файл не вдається відкрити | записується у журнал із причиною від `strerror` |
| файл не є розбірним JSON | виняток розбирача перехоплюється і записується у журнал |
| **кореневий елемент ідентичності відсутній** | пошук ведеться за *налаштованим* іменем застосунку |
| масив `annotations` верхнього рівня відсутній | |
| група тек не має елемента `db` | |
| група тек не має елемента `annotations` | |
| елемент `db` не має `path` | |
| **`db.path` присутній, але порожній** | порожній корінь джерела ні до чого не розв'язується |

Останні чотири перевіряються для кожної групи тек, і перша ж група, що не проходить перевірку, перериває усе завантаження - часткова база даних ніколи не повертається назовні.

Тому найменшим можливим недійсним документом є `{}`, і саме це містить друга фікстура компонентного тесту [non_empty_annotation_db_init_serialize_failure.json](/src/lib/libmain/dbs/AnnotationsDBs/tests/component/AnnotationsDirDB/ctest_data/non_empty_annotation_db_init_serialize_failure.json): дійсний JSON, немає кореневого елемента, у завантаженні відмовлено.

Варто зауважити, що невдале завантаження не відкочує базу даних до того, що вона містила раніше - `load_db()` є заміщувальною операцією, і невдача залишає її у невизначеному стані. Трактуйте `false` від нього як "з цим примірником покінчено" і будуйте новий.

Під цим шаром жорсткої перевірки є м'якіший. Група тек, чий `db.path` у порядку, але чиї окремі записи зображень спотворені - запис без `rel_path`, прямокутник без `rect` - не є тим, що формат толерує: конвертери роблять assert для цих полів, тож зневаджувальна побудова зупиниться на місці, а релізна опиниться на невизначеній території. Іншими словами: обов'язкові поля двох найглибших рівнів є обов'язковими, і виробник має їх видавати.

### Цикл читання-запису

Збереження - це не "редагування файлу, який ви завантажили", це запис свіжого документа з записів у пам'яті. Наслідки:

- ключі, яких формат не визначає - як-от об'єкт `"user"` з фікстури - **не зберігаються**;
- групи тек перебудовуються шляхом групування записів за їхніми `abs_dir_path`, і виходять упорядкованими за цим шляхом;
- усередині групи записи зберігають той порядок, який мають у пам'яті;
- кожне необов'язкове поле запису зображення записується, нульове воно чи ні;
- вивід форматується для читабельності з відступом у два пробіли;
- елемент ідентичності записується з тими іменем і версією, якими налаштовано базу даних **на момент збереження**, а це не обов'язково ті, які ніс завантажений файл.

Саме останній пункт і кусається: завантажте файл `0.10.0`, збережіть його зі значеннями за замовчуванням - і у збереженому буде `0.11.0`. Викликайте `set_app_info()` із тим, що ви вичитали через `get_app_name()` / `get_app_version()`, якщо збереження початкового штампу для вас важливе.
